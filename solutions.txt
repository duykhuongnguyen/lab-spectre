Part 1: Leaking Kernel Memory via Flush+Reload

Discussion Question 1: 256 cache lines need to be flushed, one for each possible byte value (0–255)

Discussion Question 2: If the attacker and victim do not share memory, Flush+Reload will not work, because it relies on shared memory pages being mapped into both address spaces. 
Without shared memory the attacker cannot flush the cache lines used by the victim and reload them to detect timing differences.

Part 2: Basic Spectre

Discussion Question 3: Real-world Spectre attacks exploit speculation to bypass software-enforced bounds checks and access out-of-bounds memory. By mistraining branch predictors and using microarchitectural side channels, attackers can leak secrets from anywhere in the victim’s address space, including kernel or process-private data.

Discussion Question 4: In our experiments, the attack began working with as few as 6 branch training rounds. However, because of noise we used at least 20–30 iterations to saturate the predictor’s history and overcome timing noise.

Part 3: Advanced Spectre

Discussion Question 5: We extend the speculation window by flushing part3_limit before executing the victim code. This increases the time the CPU takes to resolve the branch condition, allowing more speculative instructions (including the secret-dependent memory access) to be executed before the misprediction is corrected.

Discussion Question 6: To port the attack, we need to understand the CPU's speculative behavior, cache hierarchy, timing thresholds, and whether the victim code permits shared memory interaction. These properties can often be deduced via timing attacks and system introspection tools like perf, dmesg, or /proc/cpuinfo.
